# Учёт рабочего времени

Небольшое веб-приложение: сотрудники, таймер с описанием задачи, записи и итоги за выбранный период.
Данные хранятся в SQLite и сохраняются после перезапуска. Все данные в примерах — вымышленные.

## Стек и почему

- **Python 3.11+, только стандартная библиотека** (`http.server`, `sqlite3`, `unittest`) — ничего не нужно устанавливать, проект запускается одной командой.
- **SQLite** — один файл `timetracker.db`, достаточно для небольшой компании и не требует отдельного сервера.
- **Интерфейс** — одна страница `static/index.html` на чистом JavaScript, без сборки и фреймворков.

## Запуск

```bash
python server.py                 # http://127.0.0.1:8000, база — timetracker.db
python server.py --port 9000 --db my.db
python seed.py                   # (по желанию) вымышленные демо-данные
```

Тесты:

```bash
python -m unittest discover -s tests -v
```

Для запуска на хостинге: `python server.py --host 0.0.0.0` (порт берётся из переменной `PORT`, путь к базе — из `TIMETRACKER_DB`). Если хостинг стирает диск при перезапуске, базу нужно положить на постоянный том, иначе данные не сохранятся.

## Как пользоваться

1. Введите имя и нажмите «Добавить».
2. Напротив сотрудника впишите задачу и нажмите «Старт» (или Enter). Таймер тикает на странице, «Стоп» завершает запись.
3. В блоке «Отчёт» выберите даты (или «Сегодня / 7 дней / Месяц») — появятся итог по каждому сотруднику и список записей. Можно отфильтровать одного сотрудника.

## Структура

```
tracker.py        ядро: сотрудники, таймеры, записи, отчёты (вся бизнес-логика)
server.py         HTTP-сервер: JSON API + раздача страницы
static/index.html интерфейс
seed.py           демо-данные
tests/            test_tracker.py (ядро), test_api.py (HTTP, настоящий сервер)
```

API (JSON):

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/employees` | сотрудники + активный таймер |
| POST | `/api/employees` `{name}` | добавить сотрудника |
| POST | `/api/timer/start` `{employee_id, task}` | запустить таймер |
| POST | `/api/timer/stop` `{employee_id}` | остановить таймер |
| GET | `/api/entries?start&end[&employee_id]` | записи за период |
| GET | `/api/report?start&end` | итоги по сотрудникам |

Коды ошибок: 400 — неверные данные, 404 — не найдено, 409 — конфликт (повторный старт, дубликат имени, стоп без таймера).

## Принятые решения

- **Один таймер на сотрудника** гарантируется на уровне базы: частичный уникальный индекс `ON entries(employee_id) WHERE stopped_at IS NULL`. Проверка «в коде» не защитила бы от двух одновременных запросов, индекс — защищает.
- **Время хранится в UTC**, браузер переводит выбранные даты из локального часового пояса. Формат `YYYY-MM-DDTHH:MM:SSZ` сортируется как строка, поэтому сравнения в SQL верны.
- **Период — `[начало, конец)`**: запись относится к периоду по моменту *начала*; в интерфейсе дата «По» включается целиком. Работающий таймер считается до текущего момента.
- **Пустой отчёт — не ошибка**: сотрудники без записей возвращаются с нулями, итог — 0.

## Ошибки, найденные и исправленные

1. **Регистр кириллицы в именах (реальный баг, найден тестом).** Имя сотрудника было `UNIQUE COLLATE NOCASE`, но в SQLite `NOCASE` сворачивает регистр только у ASCII. «анна тестова» и «Анна Тестова» считались разными людьми, тест на дубликат упал. Исправление: колонка `name_key` с `casefold()` из Python и уникальность по ней; сортировка списка тоже перенесена в Python (по той же причине).
2. **Мёртвая строка в обработке ошибок (найдена при ревью).** В первой версии `server.py` внутренние ошибки обрабатывались строкой вида `self.log_error(...) if False else None` — она ничего не делала, и непредвиденные исключения терялись без следа. Заменено на `traceback.print_exc()`: клиент получает общий ответ 500, подробности остаются в логе сервера.
3. **Ошибка в тесте.** В `test_api.py` в `bytes`-литерале была кириллица (`b"{не json"`), что синтаксическая ошибка Python. Исправлено на `"...".encode("utf-8")`.

## Тесты (33)

Ядро (`tests/test_tracker.py`): добавление и дубликаты сотрудников, пустое имя; старт/стоп и длительность; **повторный запуск таймера** (отказ, исходная запись не меняется); запуск после остановки; параллельные таймеры разных сотрудников; стоп без таймера, двойной стоп; пустая задача; несуществующий сотрудник; остановка «раньше старта»; **пустой отчёт** (нет записей / нет сотрудников); суммы по сотрудникам; границы периода; работающий таймер в отчёте; неверный период; часовой пояс `+06:00`; **сохранность данных после перезапуска**.

HTTP (`tests/test_api.py`): запускается настоящий сервер на свободном порту — коды ответов, повторный старт (409), пустой отчёт (200 с нулями), неверный JSON, неизвестные маршруты, полный сценарий с остановкой и повторным запуском сервера на той же базе.

## Ограничения и что можно доработать

- Нет редактирования и удаления записей и сотрудников.
- Запись, пересекающая границу периода, целиком относится к периоду, где она началась (без разрезания по границе).
- `http.server` подходит для небольшой нагрузки; для продакшена — WSGI-сервер за прокси.
- Интерфейс проверялся на синтаксис и через API; ручной прогон в браузере стоит выполнить перед сдачей.
